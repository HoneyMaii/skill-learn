01Why this guide exists

先解释主题解决什么问题

说明该技术主题适合谁、改变了什么工作流、什么情况下不值得使用。避免泛泛而谈，优先写可操作的判断标准。

Context

使用场景

列出读者会遇到的真实任务，以及这个主题如何降低操作成本。

Boundary

适用边界

写清楚什么时候使用、什么时候继续用现有工具更稳。

Caveat

版本差异

把 CLI、API、配置和文档版本差异记录到 `source-notes.md`。

Version note

不确定的命令或 API 不要硬写成事实。先标出 caveat，再给读者检查路径。

03Workflow

        
把流程写成读者能执行的步骤

        
每一步都要有输入、动作、输出或检查点。不要只堆命令，命令后面必须解释成功信号和失败时看哪里。

  • 运行第一条命令并保存输出。
    • 
              
  • 对照预期结果完成自检。

            Common failure
            
教程不是命令列表。读者需要知道为什么运行、成功是什么样、失败时如何定位。

          

        

      


      

        
04Patterns

        
沉淀可复用模式

        
模式必须告诉读者何时使用、何时不要使用，以及下次如何迁移到类似任务。

        

          Case study
          

            
Context

            
团队需要把零散 CLI 经验转成可复用上手指南。

            
Decision

            
先冻结资料，再按任务路径组织章节，最后验证复制按钮和移动端布局。

            
Outcome

            
新成员可以按章节完成第一次实践，并能追溯每个命令的来源。

          

        

      


      

        
05Practice

        
给读者一个可复用 prompt

        
Prompt template 用于 agent 提示词、迁移模板、复盘模板或调试模板。复制按钮同样读取 canonical code。
