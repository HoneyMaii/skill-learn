面向商务团队的实战分享：用 Codex 技能把主题、风格、文案、注意点和可编辑 HTML PPT 串成一套可复用流程。

Why This Matters

对商务团队来说，PPT 不是设计活，是交付效率问题。

传统做法

  • 先写 Word，再搬到 PowerPoint。
  • 风格靠临时套模板，质量不稳定。
  • 修改一版内容，经常牵动十几页排版。

技能工作流

  • 先问清用途、受众、页数、内容状态。
  • 先看风格预览，再生成正式稿。
  • 交付一个浏览器可演示、可编辑的 HTML 文件。

Skill Basics

Skill 是把“怎么做”写进代理工作流。

它不是简单提示词，而是一份本地说明书：什么时候用、先问什么、读哪些文件、生成时必须守住哪些边界。

Mental Model SOP for AI execution

Two Skills, Two Jobs

先用 frontend-slides 定演示流程，再用 design-taste-frontend 把质感拉上去。

frontend-slides

  • 内容发现：用途、页数、内容状态、编辑需求。
  • 风格发现：先生成预览，再让用户选择。
  • 生成约束：单文件、可导航、视口安全。

design-taste-frontend

  • 避免默认模板感和紫蓝渐变套路。
  • 限制强调色、控制动效、保证移动端收敛。
  • 用工程规则表达审美判断。

Reusable Prompt

把需求写成结构化输入，输出质量会稳定很多。

关键不是把提示词写长，而是把决策点提前说清：谁看、看多久、要不要编辑、风格怎么确认。

Delivery Format

最终交付不是 PPTX，而是一个可演示、可编辑、可导出的 HTML。

演示能力

  • 方向键、空格、滚轮、触控翻页。
  • 导航点和进度条提供当前位置感。
  • 每页固定 100dvh，避免演示时滚动穿帮。

编辑能力

  • 按 E 进入编辑模式。
  • 点击文字即可改内容。
  • Ctrl+S 导出干净 HTML 文件。

Viewport Rules

演示文稿最容易翻车的地方，是内容超出视口。

frontend-slides 的硬规则是：每页固定视口高度，内容多就拆页，不允许在一页内部滚动。

viewport.csshard rule
.slide {
  height: 100vh;
  height: 100dvh;
  overflow: hidden;
}

h1, h2, p {
  font-size: clamp(min, ideal, max);
}

Design Taste Guardrails

生成过程中，design-taste-frontend 负责挡住“模板感”。

字体 用强展示字体和清晰正文字体，避免默认字形。
颜色 一个主强调色，克制使用，不做杂色拼贴。
布局 减少全居中，使用分栏、错位和强编号。
动效 只动 transform 和 opacity，并支持减少动效。

Pitfalls

团队落地时，最常见的坑不是技术，而是流程跳步。

最大坑

没有先问用途、受众、风格，就直接生成。结果看似很快，但经常返工：文案不对、语气不对、设计也不适合会议。

视口坑

一页塞太多内容，投影或小屏打开后溢出。

编辑坑

导出时没有清理编辑状态，打开文件像仍在编辑模式。

建议把它作为“商务材料初稿生产线”，而不是一次性玩具。

Week 2

Week 3

Week 4

复盘

Takeaway

先问清楚，再给预览，最后生成。

这套流程的价值不是“AI 做 PPT”，而是把商务表达、视觉选择和工程约束变成稳定可复用的生产过程。
