# 05 最佳工程实践

## 规则放置原则

优先按作用范围决定规则放在哪里：

- 项目共识进入 `.gitignore`。
- 当前 clone 的个人规则进入 `.git/info/exclude`。
- 当前用户跨仓库通用规则进入全局 ignore。

不要把个人偏好都塞进项目 `.gitignore`，也不要把团队共识只写在自己的 exclude 里。

## 项目 `.gitignore` 适合包含

- 构建产物：`dist/`、`build/`、`target/`。
- 日志：`*.log`。
- 测试输出：coverage、临时报告、快照输出中的生成物。
- 依赖缓存或包管理器生成的本地目录。
- 本项目明确不应入库的临时文件。

具体规则要根据语言和框架决定，避免盲目复制过大的模板。

## 个人 ignore 适合包含

`.git/info/exclude` 适合当前 clone 的个人噪音。

全局 ignore 适合同一用户所有仓库都不想看到的本机文件。

常见例子：

- 操作系统文件。
- 编辑器临时文件。
- 本地调试脚本输出。
- 个人工具缓存。

## 已 tracked 文件处理原则

如果文件已经 tracked，不要期待 ignore 规则改变它。

正确流程是：

1. 确认它是否应该继续被版本控制。
2. 添加合适的 ignore 规则。
3. 使用 `git rm --cached <path>` 从索引中移除。
4. 检查 `git status`。
5. 必要时提交“停止跟踪”的变更。

## 敏感信息原则

密钥、令牌、私有配置不应进入仓库。

如果敏感信息已经提交，ignore 规则只能阻止未来再次添加，不能修复已经泄露的历史。

应当：

- 立即轮换密钥。
- 移除当前仓库中的跟踪关系。
- 根据团队安全流程处理 Git 历史。
- 提供 `.env.example` 这类无敏感值的配置模板。

## 规则可读性

项目 `.gitignore` 应保持可读：

- 按类别分组。
- 用少量注释说明意图。
- 避免过宽规则误伤源码。
- 团队规则变更在 PR 中说明原因。

## 保留空目录

Git 不跟踪空目录。

如果项目需要保留目录结构，可以放一个说明文件，例如：

- `.gitkeep`
- `README.md`

如果目录内容要被忽略，但保留目录本身，需要设计更具体的 ignore 规则。

## 工程清单

最终指南可以把本节整理成可直接执行的工程清单。

### 新增 ignore 规则前

- 确认规则是团队共识、当前 clone 规则，还是个人全局规则。
- 确认规则不会误伤源码、配置模板、测试数据或文档。
- 能写窄规则时不要写过宽规则。
- 对不直观的规则加注释说明原因。

### 文件已经出现在 `git status` 时

- 先用 `git ls-files -- <path>` 判断是否已经 tracked。
- 如果已经 tracked，不要期待 ignore 规则让它消失。
- 如果要本地保留但仓库停止跟踪，使用 `git rm --cached <path>`。
- 如果仓库和本地都要删除，使用 `git rm <path>`。
- 修改后用 `git status` 复核索引变化。

### 提交 `.gitignore` 变更前

- 检查是否包含个人偏好；个人偏好应放 `.git/info/exclude` 或全局 ignore。
- 检查是否把团队需要的文件误忽略。
- 检查是否需要提供模板文件，例如 `.env.example`。
- 在 PR 或提交说明里说明规则变更原因。

### 处理敏感信息时

- 不要把 ignore 当作安全修复手段。
- 如果敏感信息已经提交，立即轮换密钥或令牌。
- 从当前版本中移除敏感文件。
- 按团队安全流程处理 Git 历史。
- 提供不含真实密钥的模板文件。

## 决策树

可以把最终指南中的判断流程写成这个顺序：

```text
遇到一个不想提交的文件
  |
  |-- 它是否已经 tracked？
  |     |
  |     |-- 是
  |     |     |
  |     |     |-- 是否要保留执行者本地物理文件？
  |     |     |     |
  |     |     |     |-- 是：添加 ignore 规则，然后 git rm --cached <path>
  |     |     |     |
  |     |     |     |-- 否：添加 ignore 规则，然后 git rm <path>
  |     |     |
  |     |     |-- 如果是敏感信息：轮换密钥，并按安全流程处理历史
  |     |
  |     |-- 否
  |           |
  |           |-- 团队都应该忽略？
  |           |     |
  |           |     |-- 是：写入 .gitignore 并提交
  |           |     |
  |           |     |-- 否
  |           |
  |           |-- 只对当前 clone 有意义？
  |           |     |
  |           |     |-- 是：写入 .git/info/exclude
  |           |     |
  |           |     |-- 否
  |           |
  |           |-- 当前用户所有仓库都想忽略？
  |                 |
  |                 |-- 是：写入全局 ignore
  |                 |
  |                 |-- 否：不要添加 ignore 规则，重新判断文件是否应该入库
```

已确认：最终最佳实践章节采用“工程清单 + 决策树”结构，帮助读者直接判断规则放置位置、tracked 文件处理方式、敏感信息处理方式和 `.gitignore` 变更审查要点。
