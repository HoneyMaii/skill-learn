# 03 已 Tracked 文件的处理

## 问题场景

最常见的困惑是：

已经把文件写进 `.gitignore`，为什么 `git status` 还是显示它被修改？

答案通常是：

这个文件已经是 tracked file。

## 关键规则

ignore 规则不会改变 Git 索引。

如果一个文件已经被 Git 跟踪，Git 会继续记录它的修改、删除和重命名。ignore 规则不会让 Git 停止追踪它。

## 正确处理流程

如果希望某个已 tracked 文件以后不再进入版本控制，但本地文件仍然保留，可以执行：

```bash
git rm --cached foo.log
```

这条命令的重点：

- 会把 `foo.log` 从 Git 索引中移除。
- 不会删除执行命令者工作区里的 `foo.log` 物理文件。
- 下一次提交会记录“仓库不再跟踪这个文件”。
- 之后需要配合 `.gitignore`、`.git/info/exclude` 或全局 ignore，避免它再次被添加。

## 为什么要加 `--cached`

初学者容易困惑：既然是 `git rm`，会不会把本地文件删掉？

需要明确区分两个命令：

```bash
git rm foo.log
```

这个命令会从 Git 索引移除 `foo.log`，同时删除工作区里的 `foo.log` 文件。

```bash
git rm --cached foo.log
```

这个命令只从 Git 索引移除 `foo.log`，保留工作区里的 `foo.log` 文件。

所以当目标是“仓库以后不要跟踪这个文件，但我本地还要保留它”时，需要使用 `--cached`。

## 推荐顺序

推荐按这个顺序处理：

```bash
echo "foo.log" >> .gitignore
git rm --cached foo.log
git status
git commit -m "stop tracking foo log"
```

如果规则只适合个人本地，不应该提交给团队，可以把 `foo.log` 写进 `.git/info/exclude`，再执行：

```bash
git rm --cached foo.log
git status
```

是否提交取决于这个文件停止被跟踪是不是团队共识。如果它本来就在共享仓库中，通常需要通过一次提交让仓库状态改变。

## 实践案例：已提交到项目仓库的日志文件

场景：

团队项目里曾经误提交了 `foo.log`。现在希望仓库以后不再跟踪它，但每个人本地仍可以保留自己的日志文件。

推荐流程：

1. 把规则写入项目 `.gitignore`，因为这是团队共识：

```gitignore
foo.log
```

2. 从 Git 索引中移除它，但保留本地文件：

```bash
git rm --cached foo.log
```

3. 查看状态：

```bash
git status
```

预期现象：

- `.gitignore` 显示为新增或修改。
- `foo.log` 显示为 deleted，意思是“将从仓库版本控制中删除”，不是说本地工作区文件已经没了。

4. 提交这次仓库规则变更：

```bash
git add .gitignore
git commit -m "stop tracking foo log"
```

5. 提交之后，`foo.log` 留在当前工作区，但不再被 Git 跟踪。后续修改 `foo.log`，普通 `git status` 不应该再显示它。

需要说明：

- 这次提交会让项目仓库停止跟踪 `foo.log`。
- 对执行 `git rm --cached foo.log` 的人来说，本地磁盘上的 `foo.log` 会保留下来。
- 对其他成员来说，拉取这次提交时，Git 会把仓库层面的删除同步到他们的工作区。也就是说，如果他们本地没有额外修改或保护这个文件，`foo.log` 可能会从他们的工作区中消失。
- 如果其他成员本地也需要保留自己的 `foo.log`，要结合团队协作流程说明清楚。
- 如果团队希望每个人都保留自己的本地日志，应在变更说明里提醒成员在拉取前备份本地文件，或在拉取后重新生成本地文件。

## 两种目标要分清

处理已 tracked 文件前，要先确认目标是哪一种。

### 目标一：仓库不再跟踪，但执行者本地保留文件

使用：

```bash
git rm --cached foo.log
```

适合：

- 本地配置文件。
- 本地日志文件。
- 每个人机器上都可能有不同内容的文件。
- 文件不应该继续由仓库统一管理，但执行者本地还要留着。

提交后效果：

- 仓库历史从这次提交开始不再跟踪 `foo.log`。
- 执行者本地物理文件保留。
- 其他人 pull 后，工作区里的 tracked 版本通常会被删除，除非他们有本地冲突或自行备份。

### 目标二：仓库和本地都删除误追踪文件

使用：

```bash
git rm foo.log
```

适合：

- 文件本来就是误提交的产物。
- 仓库不应该保留它。
- 执行者本地也不需要保留这个物理文件。

如果还要防止它以后再次被添加，需要同时写入 ignore 规则：

```bash
echo "foo.log" >> .gitignore
git rm foo.log
git add .gitignore
git commit -m "remove generated log file"
```

提交后效果：

- 仓库从这次提交开始删除 `foo.log`。
- 执行者本地物理文件也被删除。
- 其他人 pull 后，他们工作区里的 tracked 版本也会被删除。
- 之后如果本地重新生成 `foo.log`，因为 `.gitignore` 规则存在，普通 `git status` 不会把它作为 untracked file 显示出来。

### 敏感文件的特殊情况

如果误追踪的是密钥、令牌、私有配置等敏感文件，不能只做 `git rm` 或 `git rm --cached`。

还需要：

- 立即轮换密钥或令牌。
- 从当前版本中移除文件。
- 按团队安全流程处理 Git 历史中已经泄露的内容。
- 增加无敏感值的模板文件，例如 `.env.example`。

## 谨慎使用：目录批量停止跟踪

如果误提交的是构建目录，例如 `target/` 或 `dist/`，可以使用递归形式：

```bash
git rm -r --cached target/
```

这个命令会把 `target/` 目录下已经 tracked 的文件从 Git 索引中移除，但保留工作区文件。

使用前需要确认：

- 这个目录确实是构建产物或缓存，不应该进入仓库。
- 对团队来说，停止跟踪整个目录是共识。
- `.gitignore` 中已经有对应规则，例如 `target/`。
- `git status` 中显示的删除范围符合预期。

这类命令影响面比单文件更大，最终指南中应标为“谨慎使用”。

## 风险边界

不要把 `git rm --cached` 理解成“删除文件”。它移除的是索引里的跟踪关系。

但也要注意：如果这个变更被提交并推送，其他人拉取后，仓库层面会认为该文件已被删除。对于团队共享文件，这可能影响其他成员。

因此最终指南需要强调：

- 个人本地文件可以谨慎使用 `git rm --cached`。
- 团队共享文件停止跟踪前需要确认这是项目共识。
- 密钥已经提交过时，不能只靠 ignore 和 `git rm --cached` 解决，还需要轮换密钥并按安全流程处理历史记录。

## 用户确认状态

已确认：最终指南需要解释 `--cached` 的含义，加入已提交文件正确移除跟踪的实践案例，说明执行者本地物理文件和其他成员 pull 后的物理文件状态，区分“停止跟踪但本地保留”和“仓库与本地都删除”，并加入目录批量停止跟踪的谨慎使用示例。
