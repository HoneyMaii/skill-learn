# 02 三类 Ignore 机制

## 对比总览

Git 常用 ignore 入口有三类：

| 机制 | 是否提交 | 作用范围 | 适合内容 |
| --- | --- | --- | --- |
| `.gitignore` | 可以提交 | 当前仓库及团队成员 | 项目共识规则 |
| `.git/info/exclude` | 不提交 | 当前 clone | 个人本地规则 |
| 全局 ignore | 不随仓库提交 | 当前用户的所有仓库 | 跨项目个人偏好 |

三者的规则语法大体一致，核心差异是作用范围和是否共享。

## `.gitignore`

`.gitignore` 是仓库里的普通文件，可以被提交。

一旦提交，团队成员拉取后都会使用这套 ignore 规则。

适合写入：

- 构建产物，例如 `dist/`、`build/`、`target/`。
- 日志文件，例如 `*.log`。
- 依赖或缓存目录，例如特定生态下不应入库的缓存。
- 测试输出、覆盖率报告、临时产物。
- 团队共同认可不应进入版本库的文件。

不适合写入：

- 只和某个人编辑器有关的临时文件。
- 只在某台机器上产生的本地工具噪音。
- 不确定是否所有团队成员都应该忽略的文件。

## `.git/info/exclude`

`.git/info/exclude` 是当前 Git 仓库本地目录里的 ignore 文件。

它不会被提交，也不会影响别人。

适合写入：

- 个人本地脚本输出。
- 本机工具生成的临时文件。
- 只在当前 clone 中需要忽略的文件。
- 不值得污染团队 `.gitignore` 的个人习惯。

核心判断：

如果这条规则只对你当前这份 clone 有意义，放 `.git/info/exclude` 更合适。

## 全局 ignore

全局 ignore 通常通过 `core.excludesfile` 指向一个用户级 ignore 文件。

它不属于某个仓库，而是对当前用户的多个仓库生效。

适合写入：

- 操作系统生成文件。
- 编辑器或 IDE 的个人临时文件。
- 本机工具跨项目产生的缓存。
- 个人永远不想提交的本地噪音。

常见命令：

```bash
git config --global core.excludesfile ~/.gitignore_global
git config --global --get core.excludesfile
```

## 选择规则

可以用一个判断顺序：

1. 团队所有人都应该忽略吗？放 `.gitignore`。
2. 只有当前 clone 需要忽略吗？放 `.git/info/exclude`。
3. 当前用户所有仓库都想忽略吗？放全局 ignore。

## 规则语法速查

三类 ignore 机制的 pattern 语法大体一致。最终指南可以放一个短小速查表，不展开成完整语法手册。

常用写法：

```gitignore
# 忽略任意位置的 .log 文件
*.log

# 忽略仓库根目录下的 dist 目录
/dist/

# 忽略任意层级中名为 dist 的目录
dist/

# 忽略 temp 目录下所有内容
temp/*

# 反向规则：不要忽略 important.log
!important.log
```

需要强调的点：

- `*.log` 会匹配日志文件，但只对未跟踪文件起作用。
- `/dist/` 更偏向仓库根目录下的 `dist/`。
- `dist/` 会匹配多个层级中名为 `dist` 的目录。
- `!` 是反向规则，用来把前面忽略掉的文件重新纳入候选范围。
- 反向规则无法让已被父目录整体忽略且目录本身不可见的深层文件自动重新出现，复杂场景需要谨慎设计规则。
- 注释用 `#` 开头，适合解释规则意图。
