01Overview

先把 Trellis 看成流程层

Trellis 的核心价值不是“让模型更聪明”，而是让 AI 编码有稳定流程：先收敛任务，再读取规范，然后执行、检查、复盘和归档。

任务

当前事实

需求、PRD、验收标准、研究记录和本次任务上下文。

规范

复用规则

架构约定、测试习惯、命名规则和团队长期记忆。

检查

交付约束

对照 PRD、spec、lint、type-check 和 test，减少跑偏。

02Why Trellis exists

为什么单次聊天不够用

一次聊天可以解决单点问题，但真实项目会持续演进。缺少工作流时，模型很容易忘记规则、扩大范围、跳过验证，或者让你反复解释同一套上下文。

没有 Trellis 时

  • 任务边界只藏在聊天里。
  • 项目规范每次都要重新解释。
  • 检查依赖模型自觉。
  • 经验很难沉淀到下一次任务。

有 Trellis 后

  • 任务上下文被写入 `.trellis/tasks/`。
  • 可复用规则进入 `.trellis/spec/`。
  • 实现后有 check 阶段对照要求。
  • 完成后归档和 journal 形成记忆。
一句话判断 如果任务跨多个文件、需要测试、需要记住团队约定，Trellis 才开始有明显收益。
03Mental model

三个目录决定上下文边界

新手最容易混淆的是“任务事实”和“长期规范”。先记住这三层，后面的命令才有意义。

当前任务放 tasks；长期规则放 spec；个人过程放 workspace。

这是整套指南最重要的心智模型。
1
.trellis/tasks/本次任务的 PRD、验收标准、研究记录和归档。
2
.trellis/spec/未来任务会复用的项目规范和团队约定。
3
.trellis/workspace/<user>/个人 journal、session 记忆和工作痕迹。
常见误区 不要把 `.trellis/spec/` 当作任务垃圾桶。只有未来会反复使用的规则才应该进入 spec。

前置条件

Node.js 18+ 与 Python 3.9+

先确认基础运行环境，再初始化项目。初始化后会出现 `.trellis/`、`.codex/`、`.agents/skills/` 和 `AGENTS.md` 等文件。

Codex hooks

需要显式启用

在 `~/.codex/config.toml` 打开 hooks。Codex 0.129+ 通常还需要在 Codex 中运行 `/hooks` 并批准 Trellis hook。

~/.codex/config.toml
[features]
hooks = true
[features] hooks = true
第一次建议 保持 `codex.dispatch_mode: inline` 默认路径。只有验证稳定后，再考虑旧式 sub-agent dispatch 或更复杂自定义。
05Complete walkthrough

从第一条任务跑完整闭环

第一次任务不要选迁移、重构或跨系统改造。用一个能在一轮里闭环的小功能观察 Trellis 的文件、PRD、check 和归档行为。

1
初始化 demo 仓库先看清 Trellis 写入了哪些目录和平台配置。
2
描述任务例如：添加一个 settings 页面，包含校验和测试。
3
审阅 PRD确认验收标准、范围外事项和测试要求。
4
实现并检查让 Codex 按上下文实现，再跑 Trellis check。
5
沉淀 spec只有可复用经验才写入 `.trellis/spec/`。
6
最后 finish-work代码工作完成并经过提交/审查后，再做归档和 journal。

06Everyday patterns

把日常任务放进固定模式

Trellis 能让 Codex 更稳，但前提是任务输入清楚。这里的目标不是写长 prompt，而是明确目标、范围、验收标准和禁止事项。

Feature

功能任务

说明用户价值、涉及模块、验收标准、测试要求和明确的 out of scope。

Bugfix

修复任务

先复现，再最小化，再修复。复杂 bug 修完后用 break-loop 复盘。

Research

纯调研任务

明确“只读不改代码”，输出发现、风险、建议和后续任务拆分。

控制范围的关键词 “先写 PRD 等我确认”“只调研不写代码”“不要修改 X 模块”“验收标准必须包含测试”。这些比泛泛说“仔细一点”有效。
07Pitfalls

这些坑会让流程失真

Hook

忘记批准 hooks

Codex hook 批准会影响自动上下文注入。先确认 `hooks = true` 和 `/hooks` 批准 Trellis hook 的状态。

Spec

把 spec 写成流水账

spec 应该是未来会复用的规则，不是本次任务的过程记录。

Dispatch

过早切 sub-agent

第一次先用 inline。上下文传递稳定后，再评估其他 dispatch 模式。

Finish

finish-work 时机太早

finish/archive 不是代码审查或 commit 的替代品。先完成代码、测试、审查和提交，再归档。

重要仓库前先看 auto-commit 理解 `session_auto_commit` 的行为。如果不希望自动 journal/archive 提交，先按项目策略关闭或调整。
